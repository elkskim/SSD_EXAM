\section{Introduktion}

\subsection{Projektets Formål}
Mit mål med opgaven er, at demonstrere hvordan man kan implementere 
sikkerhedsforanstaltninger i et system der håndterer "audit logs". Fokus ligger på at sikre integritet af logs ved hjælp af hash-kæder og HMAC.
Samtidigt vil jeg belyse de udfordringer og overvejelser der er forbundet med at implementere sådanne mekanismer i praksis.

\subsection{Afgrænsning}
Projektet fokuserer udelukkende på implementeringer af kryptografiske tricks for at sikre integriteten af audit logs.
Det vil ikke dække andre aspekter af sikkerhed, hverken adgangskontrol eller databeskyttelse.

\section{System-Arkitektur}

\subsection{Overordnet Design}

Systemet består af fire hovedkomponenter som arbejder sammen for at sikre integritet og autentificitet af audit logs. 
Arkitekturen er bygget omkring princippet om append-only logs med kryptografisk binding mellem successive entries.

\subsection{Komponenter}

\subsubsection{AuditLog (Kerne)}
Hovedklassen som håndterer oprettelse af nye log entries. Den koordinerer med KeyManager for at signere entries og sender dem til JsonLogStorage for persistering. Hver entry linkes til den forrige gennem hash-værdier.

\subsubsection{KeyManager}
Administrerer kryptografiske nøgler og deres versioner. Tillader nøglerotation uden at ødelægge verificering af ældre entries. Holder styr på hvilken nøgleversion hver entry blev signeret med.

\subsubsection{LogVerifier}
Verificerer integriteten af hele log-kæden. Gennemgår hver entry og kontrollerer:
\begin{itemize}
    \item At hash-kæden er intakt (prevHash matcher forrige entry)
    \item At HMAC er gyldig med den korrekte nøgleversion
    \item At ingen entries er slettet eller manipuleret
\end{itemize}

\subsubsection{JsonLogStorage}
Håndterer persistering af log entries til disk i JSON-format. Implementerer append-only principper og giver læseadgang til hele historien.

\section{Datamodeller}

\subsection{Primære Datastrukturer}

Systemet arbejder med tre centrale datastrukturer: \texttt{LogEntry}, \texttt{KeyVersion}, og \texttt{VerificationReport}.

\subsubsection{LogEntry}

En \texttt{LogEntry} repræsenterer en enkelt hændelse i audit log-kæden:

\begin{itemize}
    \item \textbf{Timestamp}: UTC-tid for når hændelsen blev registreret
    \item \textbf{Event}: Streng der beskriver typen af hændelse (f.eks. ``USER\_LOGIN'', ``FILE\_MODIFIED'')
    \item \textbf{Data}: Vilkårlig data forbundet med hændelsen
    \item \textbf{PrevHash}: SHA256-hash af den forrige entry - danner kæden
    \item \textbf{Hash}: SHA256-hash af denne entry's indhold
    \item \textbf{Hmac}: HMAC-SHA256 signatur for autentificitet
    \item \textbf{KeyVersion}: Hvilken nøgleversion blev brugt til at signere denne entry
\end{itemize}

\subsubsection{KeyVersion}

Repræsenterer en kryptografisk nøgle og dens metadata:

\begin{itemize}
    \item \textbf{Version}: Numerisk identifikator (1, 2, 3, osv.)
    \item \textbf{SecretKey}: Den faktiske hemmelighed brugt til HMAC
    \item \textbf{CreatedAt}: Hvornår nøglen blev oprettet
    \item \textbf{IsActive}: Om dette er den nuværende nøgle for nye entries
\end{itemize}

\subsubsection{VerificationReport}

Detaljeret rapport fra verificering af log-integritet:

\begin{itemize}
    \item \textbf{IsValid}: Boolean - hele kæden gyldig?
    \item \textbf{TotalEntries}: Antal entries der blev kontrolleret
    \item \textbf{ValidEntries}: Hvor mange var gyldige
    \item \textbf{InvalidEntries}: Hvor mange fejlede
    \item \textbf{FirstInvalidEntryIndex}: Indeks på første fejl (hvis nogen)
    \item \textbf{ErrorMessage}: Beskrivelse af hvad der gik galt
    \item \textbf{VerificationTime}: Hvornår verificeringen blev udført
\end{itemize}

\section{Implementering}

\subsection{Teknologivalg}

Projektet er implementeret i \textbf{C\# (.NET 9)} med følgende begrundelser:

\begin{itemize}
    \item \textbf{System.Security.Cryptography}: Built-in kryptografisk bibliotek med SHA256 og HMAC-SHA256
    \item \textbf{JSON-serialisering}: Læsbar persistering af entries til disk
    \item \textbf{Stærk typesikkerhed}: C\#'s typesystem opdager fejl ved compile-time
    \item \textbf{Exception handling}: Præcis fejlhåndtering gennem hele systemet
\end{itemize}

\subsection{Centrale Funktioner}

\subsubsection{Entry Appending}

\texttt{AuditLog.Append(event, data)} tilføjer en ny entry:
\begin{enumerate}
    \item Hent hash fra sidste entry (eller ``0'' hvis tom log)
    \item Generer nuværende timestamp
    \item Opbyg entry-indhold fra timestamp, event, data, prevHash
    \item Beregn SHA256 af indhold
    \item Beregn HMAC med aktiv nøgle
    \item Opret LogEntry-objekt
    \item Gem til disk via storage-interface
\end{enumerate}

\subsubsection{Integrity Verification}

\texttt{LogVerifier.VerifyWithReport(entries)} verificerer hele kæden og rapporterer problemer:
\begin{enumerate}
    \item For hver entry: check at \texttt{prevHash} matcher forrige entries \texttt{hash}
    \item Hent den korrekte nøgleversion baseret på entries \texttt{keyVersion}
    \item Genberegn HMAC - skal matche lagret værdi
    \item Genberegn SHA256-hash - skal matche lagret værdi
    \item Hvis fejl findes: rapportér indeks og årsag
    \item Returnér detaljeret rapport med statistik
\end{enumerate}

\subsubsection{Key Rotation}

\texttt{KeyManager.RotateKey()} introducerer ny nøgle:
\begin{enumerate}
    \item Generer ny hemmelighed med \texttt{RandomNumberGenerator}
    \item Gem ny nøgle med version nummer og timestamp
    \item Markér som aktiv
    \item Gamle nøgler gemmes for at verificere historiske entries
\end{enumerate}

\subsection{Lagring og Persistering}

\texttt{JsonLogStorage} håndterer persistering:

\begin{itemize}
    \item \textbf{Append-only}: Nye entries føjes til slutningen af JSON-fil
    \item \textbf{JSON-format}: Human-readable struktur gør manuel inspektion muligt
    \item \textbf{Atomare operationer}: Hele lister skrives på én gang for consistency
    \item \textbf{Deserialisering}: Læs entries fra disk og rekonstruer objekter
\end{itemize}

Eksempel på lagret JSON-struktur:
\begin{lstlisting}
[
  {
    "timestamp": "2026-05-29T22:30:00Z",
    "event": "USER_LOGIN",
    "data": "Admin login",
    "prevHash": "0",
    "hash": "a3f2e1c9...",
    "hmac": "c5e9d1a2...",
    "keyVersion": 1
  }
]
\end{lstlisting}

\section{Verifikation og Test}

\subsection{Test-Strategi}

Systemet verificeres gennem tre lag:

\begin{enumerate}
    \item \textbf{Hash-kæde integritet}: Hver entry skal linke korrekt til den forrige
    \item \textbf{HMAC autentificering}: Hver entry skal have gyldig signatur fra korrekt nøgle
    \item \textbf{Hash konsistens}: Genberegnet SHA256 skal matche lagret værdi
\end{enumerate}

Hvis nogle af disse fejler, rapporteres:
\begin{itemize}
    \item Præcis hvilken entry fejlede
    \item Hvilken check der fejlede (prevHash, HMAC, eller hash)
    \item Hvornår fejlen blev detekteret
    \item Samlet statistik over gyldige og ugyldige entries
\end{itemize}

\subsection{Demonstrativ Test}

Demo-program (\texttt{Program.cs}) udfører følgende scenarier:

\begin{enumerate}
    \item \textbf{Opret initial log}: Flere normale entries tilføjes
    \item \textbf{Verificer initial log}: Alle entries skal være gyldige
    \item \textbf{Nøglerotation}: Ny nøgle introduceres
    \item \textbf{Tilføj entries med ny nøgle}: Entries signeres med ny nøgle
    \item \textbf{Verificer igen}: Hele kæde med blandet nøgleversioner skal være valid
    \item \textbf{Tampering-test}: Manipulér en entry og vis at verificering fejler
    \item \textbf{Rapportér resultater}: Detaljerede rapporter vises for hver test
\end{enumerate}

Disse tests demonstrerer systemets evne til at:
\begin{itemize}
    \item Bevare integritet over lange perioder
    \item Håndtere nøglerotation uden at miste verificering
    \item Detektere enhver manipulation med præcision
\end{itemize}

\subsection{Designmønstre}

\textbf{Dependency Injection}: \texttt{AuditLog} modtager \texttt{KeyManager} og \texttt{ILogStorage} via konstruktør, gør systemet modulært og testbart.

\textbf{Strategy Pattern}: \texttt{ILogStorage} interface tillader forskellige lagringsimplementeringer uden at ændre kernalogin.

\textbf{Immutable DataModels}: \texttt{LogEntry} har kun read-only properties, forhindrer uhørt modificering af historiske data.

\section{Konklusion}

Dette projekt har demonstreret, hvordan man kan implementere et robust og tamper-evident audit log system ved hjælp af relativt simple kryptografiske primitiver.

\subsection{Resultater}

Systemet opfylder sine kernekrav:
\begin{itemize}
    \item \textbf{Integritet}: Hash-kæder sikrer, at enhver ændring af historiske data detekteres
    \item \textbf{Autentificitet}: HMAC-signaturer beviser, at entries blev oprettet af systemet selv
    \item \textbf{Nøglerotation}: Gamle entries forbliver verifiable, selvom nøgler roteres
    \item \textbf{Transparens}: JSON-format gør det muligt at inspicere logs uden særlige værktøjer
\end{itemize}

\subsection{Sikkerhedsovervejelser}

\subsubsection{Styrker}
\begin{itemize}
    \item Hash-kæder og HMAC er matematisk vellykkede mekanismer
    \item Systemet detekterer tampering, sletning og forfalskelse
    \item Nøglerotation uden at miste verificering af historiske data
\end{itemize}

\subsubsection{Begrænsninger}
\begin{itemize}
    \item Hvis krypteringsnøglen blir kompromitteret, kan nye entries forges
    \item Systemet beskytter ikke mod påtvunget sletning af hele log-filen
    \item Ingen redundans eller backup-mekanismer implementeret
    \item Kræver sikker nøglestorage (uden for denne projects scope)
\end{itemize}

\subsection{Afsluttende Bemærkninger}

Projektet viser, at ``Security by Design'' ikke nødvendigvis kræver kompleks kryptografi. Ved at kombinere velkendte primitiver (SHA256, HMAC) med god arkitektur (append-only logs, nøgleversioner) kan man opnå stærke sikkerhedsgarantier for audit logs.

I en produktionsmiljø ville man skulle tilføje:
\begin{itemize}
    \item Sikker lagring af krypteringsnøgler (hardware security modules, key vaults)
    \item Distribueret redundans af logs
    \item Adgangskontrol til log-data
    \item Compliance med GDPR, CRA og anden lovgivning
\end{itemize}

Denne implementation tjener som et solidt fundament for disse yderligere forbedringer.
